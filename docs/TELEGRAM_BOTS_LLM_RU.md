# Telegram QuantDeus: независимые боты и ответы ИИ

## Как устроены ответы

- **QuantDeus Agent** принимает сообщения через `/api/quantdeus/telegram`, использует собственный токен, команды и описание.
- **QuantDeus Store** принимает сообщения через `/api/quantdeus/telegram?bot=store`, использует **другой** токен. Токен Agent никогда не служит запасным для Store.
- Каждому боту Telegram назначает отдельный защищённый webhook; секрет выводится из его токена. Номера входящих сообщений и ограничения частоты не смешиваются.
- В обоих ботах команда `/agents` открывает реестр агентов, а сообщения отправляются от имени именно того Telegram-бота, которому написал человек.
- Общение и описания ботов — на русском языке. Технические идентификаторы остаются неизменными.

## Что проверить у владельца

1. **GitHub Secrets**: https://github.com/quantdeus/quantdeus.github.io/settings/secrets/actions — `TELEGRAM_BOT_TOKEN` и `QUANTDEUS_STORE_TELEGRAM_BOT_TOKEN` (либо `TELEGRAM_STORE_BOT_TOKEN`). Это разные токены. Не публиковать их.
2. **Vercel → quantdeus → Settings → Environment Variables**: https://vercel.com/ — разместить **тот же** токен Agent как `TELEGRAM_BOT_TOKEN` (или действующий `Telegram_bot_token`), а Store — отдельно как `TELEGRAM_STORE_BOT_TOKEN`. Для упоминаний Store в группах при необходимости добавить `QUANTDEUS_STORE_TELEGRAM_BOT_USERNAME` без символа @.
3. Повторно развернуть Vercel с новыми переменными. Затем запустить https://github.com/quantdeus/quantdeus.github.io/actions/workflows/telegram-bot.yml с пустым `telegram_update_b64`. Должно отображаться `store_webhook_ok: true` и `llm_smoke_ok: true` для работающей модели. Отсутствие Store-токена видно в логах, а не маскируется под успех.
4. Проверить `/start`, `/agents`, `/data Кто ты?` и обычный вопрос **по отдельности каждому боту**. Проверить `getWebhookInfo` каждого бота: должны быть разные адреса (для Store — `?bot=store`), не должно быть накопившихся входящих сообщений или ошибок доставки. Никогда не показывать токены в логах.

## LLM и лимиты

Обычный чат сначала использует закрытый канал OpenClaw с ограниченными правами чтения. Если тот не дал ответ, сервер пробует прямое текстовое подключение к уже настроенному провайдеру, **без Vercel Sandbox**. Приоритет: Hermes → Cerebras → Groq → OpenRouter. Требуются действующие серверные реквизиты провайдера и реальная модель; тестовые ответы не считаются успешным LLM.

Для существующего подключения Hermes используются `HERMES_LOCAL_BASE_URL`, `HERMES_LOCAL_API_KEY`, `HERMES_CLOUD_MODEL`. Дополнительные резервные варианты: `CEREBRAS_API_KEY`, `GROQ_API_KEY`, `OPENROUTER_API_KEY`. Публичные запросы не получают права на изменения сайта или GitHub, а все ответы продолжают проходить QuantDeus Shield.

**Важный факт на 17.10.2026:** в логах Vercel OpenClaw есть ошибка 402 — месячный лимит Vercel Sandbox исчерпан до 01.11.2026. Это подтверждает проблемы задач, использующих Sandbox, но не доказывает отказ каждого обычного Telegram-диалога. Резервный текстовый LLM работает только если отдельный провайдер доступен; проверить это окончательно может реальный тест /data и журналы ответа.

## Проверка изменений без отправки настоящих сообщений

В GitHub CI запускается `node scripts/qa/telegram-bot-routing.mjs`: проверяет маршруты ботов, раздельные токены, ограничения и резервную LLM с поддельным провайдером. Это проверка кода, **не** доказательство доступности живого Telegram или провайдера.
