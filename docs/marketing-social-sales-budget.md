# Мартышки QuantDeus: экономия API и рост продаж

**Цель:** полезный контент → добровольный переход → заявка → подтверждённый заказ. Просмотры и подписчики — не доказательство продаж.

## Режим работы и пределы

- Плановая статистика запускается **один раз в сутки** (07:19 UTC). Повторные ручные проверки обычно не нужны.
- Один запуск расходует не более **1 обращения к списку подключений Composio + 1 запроса статистики YouTube + 1 запроса VK** (если соответствующие секреты и подключения работают). Лимиты закреплены в скрипте.
- GitHub Actions → «QuantDeus — экономная аналитика YouTube и VK» → «Запустить вручную»: по умолчанию режим **test-only**, который запускает локальные тесты и делает **0 внешних API-запросов**. Для фактической статистики явно выберите **read-stats**.
- На ошибке 429/квоте — **остановиться без автоматической повторной попытки**. Не обходить дневной лимит созданием дополнительных учётных записей или бесконечными ретраями.
- **Загрузка Shorts и ответы на комментарии не автоматизированы** этим workflow. Защита публикаций: только подтверждённый канал, проверенное медиа, разрешённая публикация, один уникальный ID ролика, и не более одной инициированной попытки при неизвестном результате. После 429 ждать восстановления квоты; не перезапускать по кругу.
- Уже существующие дорогие контуры (Copilot/OpenClaw) требуют отдельного аудита нагрузки; этот PR не меняет их расписание.

## Что продвигаем и куда ведём

Выбираем только реально существующие услуги: [автоматизация бизнеса](https://quantdeus.ru/services/) и [заявка на концерт Ксении Чередниковой](https://quantdeus.ru/ksenia-cherednikova/). По каталогу цена рассчитывается индивидуально, **не обещать неподтверждённую фиксированную цену, скидку или гарантированный результат**.

Перед публикацией ролика/клипа с одним ценным советом либо проверенным кейсом:

```bash
node scripts/social-sales-links.mjs youtube automation q4-2026 short-01
node scripts/social-sales-links.mjs vk concert q4-2026 clip-01
```

Инструмент выдаёт готовую ссылку и простой призыв к действию. Он **не обращается ни к YouTube, ни к VK**, не требует токенов и ничего не публикует.

- Для YouTube Shorts: один конкретный тезис → короткий пример/демонстрация → релевантная ссылка в описании/профиле, без ложных утверждений о кликабельности ссылок в Shorts.
- Для VK Клипов: полезный результат → один призыв оставить заявку → ссылка на нужную услугу в доступном формате VK.
- Не создавать десятки почти одинаковых роликов: один подтверждённый материал → адаптированные форматы на две площадки → измерить качество трафика → улучшить следующий материал.

## Как учитывать продажи без самообмана

Каждая кампания: `campaign_id`, `content_id`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`. Сбор UTM-переходов **требует работающей аналитики на целевых страницах**; создание ссылки само по себе не измеряет конверсии.

Только подтверждённые источниками результаты добавляются в `coordination/growth/marketing-scorecard.json`. Для каждой кампании:
- `visits`: реальные посещения из веб-аналитики;
- `qualified_leads`: проверенные заявки с достаточным контекстом;
- `paid_orders`: подтверждённые оплаченные заказы, а не письма или клики;
- `revenue_rub`: реальная сумма соответствующих оплат в рублях;
- `evidence`: ссылка на допустимый безопасный агрегат/отчёт, **без персональных данных и реквизитов**.

Команда для отчёта: `node scripts/marketing-funnel-report.js`. Если число неизвестно — `null`, а не выдуманный ноль. Если аналитика сайта или кассы ещё не связана с кампаниями, влияние социальных сетей на продажи **не доказано**.

## Маркетинговый цикл

**Synthesis** готовит одно полезное видео и VK-версию из проверенного материала. **Herald** готовит одну версию описания с отслеживаемой ссылкой; перед публикацией получает разрешение владельца. **Unity** проверяет, какая услуга и аудитория соответствуют материалу. **Data** ежедневно читает агрегаты, раз в неделю сравнивает заявки и оплаченные заказы. Если доказательств роста нет — не повышать интенсивность публикаций/API.

Контрольные вопросы недели: появились ли целевые переходы? Были ли реальные заявки? Сколько из них оплачено? Нужно ли менять *сообщение или предложение*, а не частоту вызовов API?

Внешние публикации, массовые ответы, платная реклама, новые цены и любые изменения платёжных данных без отдельного согласования запрещены.
