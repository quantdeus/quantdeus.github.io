# Galaxy Swarm × GitHub — интеграционная архитектура v1

Статус: проектная спецификация. Документ не означает, что новые агенты, workflows или сервисы уже развёрнуты.

## 1. Принципы

- GitHub — журнал изменений, очередь проверяемой работы и хранилище артефактов, а не единственный runtime для всех агентов.
- Не менять опубликованный сайт и production-код ради первого прототипа.
- Начинать с документации и офлайн-симуляции; кодовые изменения — в feature branch и через review.
- Агентам выдавать минимально необходимые права.
- Любой отчёт о выполнении должен ссылаться на проверяемый артефакт: commit, run, issue, test output или лог.

## 2. Компоненты

```text
Пользователь / задача
        |
        v
Intake & Policy Gate
        |
        v
Galaxy Swarm Orchestrator ---- Budget / Rate Limits / Retry
        |
        +--> Research & Source Collector
        +--> Pattern Miner / Eureka Generator
        +--> Adversarial Reviewer (Sherlock/Tuvok)
        +--> Experiment Planner / Data Analyst
        |
        v
Evidence Gate + Human Override
        |
        +--> GitHub Issues: задачи, гипотезы, ошибки
        +--> Feature Branch / Pull Request: изменения кода и документации
        +--> GitHub Actions: lint, tests, schema validation, security checks
        +--> Artifacts/Reports: результаты проверок
        |
        v
Outcome Memory / Metrics / Daily Observer Report
```

## 3. Рекомендуемые GitHub сущности

- **Issue** — единица задачи или гипотезы; метки: `swarm`, `hypothesis`, `needs-evidence`, `human-review`, `experiment`, `verified`, `rejected`.
- **Feature branch** — изолированная рабочая область, например `feat/intuition-engine-pilot`.
- **Pull Request** — изменения с кратким обоснованием, доказательствами, тестами и rollback plan.
- **GitHub Actions** — воспроизводимые проверки; workflow не должен исполнять произвольные команды из текста Issue.
- **Artifacts** — отчёты и тестовые результаты; хранить только безопасные, необходимые данные.
- **CODEOWNERS / branch protection** — человеческая проверка критических путей и защиты основной ветки.

## 4. Протокол одной задачи

1. Intake создаёт `task_id`, цель, ограничения, критерий успеха и максимальный бюджет.
2. Оркестратор назначает роли и ограничивает число параллельных исполнителей.
3. Исследователь прикрепляет источники; генератор создаёт альтернативные гипотезы.
4. Критик пытается опровергнуть каждую гипотезу.
5. Планировщик предлагает дешёвую безопасную проверку.
6. Evidence Gate выбирает: `report_only`, `run_safe_test`, `request_human_approval` или `reject`.
7. При необходимости создаётся Issue или feature branch; код не попадает прямо в production.
8. CI проверяет формат, тесты, секреты и изменения в разрешённых путях.
9. Наблюдатель публикует только подтверждённые результаты и ссылки.
10. Outcome Memory фиксирует фактический исход и стоимость.

## 5. Контроль действий

По умолчанию разрешены: чтение доступных файлов, анализ, генерация гипотез, подготовка отчёта и предложение diff.

Отдельное одобрение нужно для: записи в основную ветку, изменения workflows/permissions, публикации релиза, внешних сообщений, платежей, удаления, изменения production или работы с чувствительными данными.

Запретить автоматически: вывод секретов в логи, запуск непроверенного кода из Issue/PR, повышение собственных прав, отключение проверок, обход Human Override.

## 6. GitHub Actions — будущий безопасный минимум

На пилоте добавить workflow только после отдельного review. Рекомендуемые проверки:
- Markdown lint / links (если поддерживается проектом);
- JSON/YAML schema validation для артефактов;
- unit tests для scoring и policy gate;
- secret scanning;
- dependency/security checks;
- минимальные permissions, например read-only по умолчанию;
- pinning сторонних Actions на commit SHA;
- concurrency group и timeout;
- никакой автоматической записи в `main` из исследовательского агента.

## 7. Работа с масштабом

Планировать тысячи зарегистрированных агентов как каталог ролей/исполнителей, но запускать только нужное число. Использовать очередь, лимиты по провайдеру, стоимость на задачу, дедупликацию, кэш источников, backoff и circuit breaker.

Сначала доказать качество на 3–5 ролях и десятках задач. Увеличивать параллелизм только после измерения качества, цены и надёжности.

## 8. Наблюдаемость

Каждый запуск получает `run_id`, `task_id`, версию конфигурации и статус. Итоговый отчёт включает:
- выполненные и пропущенные проверки;
- ссылки на источники/Issue/PR/CI;
- гипотезы и их evidence grade;
- ошибки и блокировки;
- фактические затраты, если измерены;
- следующий безопасный шаг.

Если данные недоступны, указывать `UNKNOWN`, не подменять это предположением об успехе.
